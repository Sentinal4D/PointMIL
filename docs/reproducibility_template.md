# Reproducibility

This document records what the release code reproduces, how the numbers were
obtained, and where they differ from the paper. It is generated by
`scripts/make_reproducibility.py` from the authors' evaluation outputs (original
checkpoints re-evaluated with the release code, and models re-trained with it); those
intermediate files are not part of the repository.

## How the paper numbers were produced, and what that means here

1. **Validation split = test split.** For every dataset the original training runs
   used the test split (of each fold) for checkpoint selection and early stopping.
   ATLAS-1 has a validation subset (`splits/atlas1/split0.csv`), but the paper runs did
   not use it. The configs keep this behaviour (`train.val_split: test`) so that the
   paper runs can be reproduced; `train.val_split: holdout` (or `validation` for
   ATLAS-1) gives a proper validation set.
2. **Best-over-epochs values.** Some Table 2 cells (notably IntrA PointMIL(Trans.)
   97.3 / 97.5, RBC PointMIL(PointNet) 69.0 / 69.1, the PointMLPElite rows) only match
   the original run logs when the per-fold metric is the maximum over epochs of the
   validation metric (which, by point 1, is the test metric). The release trainer
   writes both conventions to `summary.json`: `test_best` (test metrics of the
   checkpoint selected on the validation metric), `test_last` (final epoch) and
   `highest_val` (maximum over epochs). The tables below report the test metrics of
   the selected checkpoint unless stated.
3. **Pooling per cell.** Table 2 reports one PointMIL row per backbone; the pooling
   head behind each cell differs (see `docs/EXPERIMENTS.md`). Where no run folder
   could be matched to a published value, the closest run is evaluated and the notes
   column says "source run not identified".
4. **Interpretability evaluation set.** Table 1, Supp. Table 3 and Fig. 6 evaluate
   AOPCR and NDCG@n on all 116 annotated aneurysm segments for every fold model, so
   most evaluation cases were in each model's training folds (`--split annotated`).
   Both AOPCR and NDCG@n score the interpretation of the aneurysm class (class 1).
5. **ATLAS-1 used a single train/val/test split**, not 5-fold cross-validation as the
   supplementary material states. The RBC Transformer row is a mean over 4 folds
   (fold 0 is missing from the original runs). The IntrA PointMLPElite rows match
   single fold-1 runs; for RBC PointMLPElite only fold-2 runs exist and none matches the
   published values. 5-fold PointMLPElite runs were added with the release code (table
   below).
6. **Randomness at test time.** Each cloud is subsampled to 1024 random points at
   evaluation, so re-evaluating a checkpoint reproduces the logged value up to a few
   tenths of a percent. ModelNet40 CurveNet dagger and PointMLPElite dagger rows were
   produced with the CurveNet and PointMLP repositories (different checkpoint formats);
   those checkpoints were not ported and are not re-evaluated here.
7. **ATLAS-1 test-time sampling.** The original ATLAS-1 loader reduced each 4096-point
   cloud to 1024 points with farthest point sampling from a random start point, at
   training and at every evaluation. The accuracy stored in each original checkpoint,
   and the published ATLAS-1 values, are therefore the best of about 100 evaluations
   with different random subsets. The release code starts farthest point sampling at
   point 0 at test time, which gives one deterministic value per checkpoint and reads
   0.5 to 2.6 points lower than the paper. Evaluating the same checkpoints several
   times with random starts shows the size of the effect:

   The spread between draws is 0.2 to 1.0 points (one standard deviation), and the
   best of only ten draws already comes within 0.1 to 1.1 mACC points of the published
   values. The published ATLAS-1 values should be read as best-case values; the mean
   over draws (or the deterministic value) is the fairer comparison between models.

8. **Numerical equivalence of the port.** All ported modules load the original
   weights and reproduce the original forward pass (`tests/equivalence`, tolerance
   1e-4 or tighter). The original fused CurveNet-MIL class was never
   committed and was reconstructed from the checkpoint tensor shapes; its
   re-evaluated metrics below are the check.
9. **Head layouts that changed between runs.** The original code changed while the
   experiments ran, and some runs used uncommitted versions. The release code supports
   every layout found in the checkpoints: the instance-classifier variants of the IntrA,
   RBC and ModelNet40 runs (including features raised from d to 4d before conjunctive
   pooling and a narrowing d, d/2, d/4 classifier), two OpenPoints instance heads, and
   two attention-pooling bag classifiers (an MLP on the concatenated attention-weighted
   mean and max, or one linear layer on the mean, used by the ATLAS-1 DGCNN, PointNet and
   PointMLPElite and ScanObjectNN PointMLPElite runs). Layouts are read from the
   checkpoint where the tensor shapes determine them, and are written in the configs
   where they do not (`attention_classifier`). Each choice was confirmed by reproducing
   the accuracy stored in the original checkpoint.

10. **RBC point clouds.** Supplementary section 13.2 describes marching cubes "with
    Laplacian smoothing". The RBC `.ad` files the models were trained and evaluated on were
    obtained ready-made; they are the unsmoothed marching-cubes vertices (with normals) of
    the public 3D masks. `scripts/prepare_rbc.py` recreates exactly those files from the
    masks (byte-identical for all 825 cells), since they cannot be redistributed.
11. **CurveNet CLAIM interpretability (Table 1).** For the CurveNet global-average-pooling
    (CLAIM) baseline the release code gives AOPCR 2.766 +/- 0.614 and NDCG@n 0.314 +/- 0.042
    on the original checkpoints, against 1.363 / 0.252 in the paper. The classification
    accuracy of the same checkpoints matches, but the published interpretability values
    could not be traced to any notebook output, and the CurveNet-MIL class was reconstructed
    from the trained weights. The release-code values are the reference values for this
    repository.

## Models re-trained from scratch with the release code

Every run below used `scripts/train.py` with the config of the same name, seed 42, on
one Quadro RTX 6000 shared with other jobs (train time is wall clock on that shared
GPU). The validation split is the test split, as in the original runs (point 1), so
"test mACC (best ckpt)" is the test metric of the checkpoint chosen on that split and
"max over epochs" is the largest value reached during training, which is the
convention behind the published values. Both are measured on the same split, but every
evaluation draws a new random subsample of each cloud, so the maximum over epochs sits
1 to 3 points above the re-evaluated selected checkpoint (the same effect as for
ATLAS-1, point 7). Each model's exact training config is stored with it on the Hub.
AOPCR / NDCG@n are the Table 1 metrics (contextual attention k = 12, all 116 annotated
segments).

The re-trained IntrA PointMIL(Trans.) conjunctive model reaches 96.2 / 96.1 mACC / F1
over 5 folds under the paper's convention (paper: 97.3 / 97.5), and AOPCR 17.1 / NDCG@n
0.602 (paper: 16.3 / 0.610). Its selected checkpoints give 93.6 / 94.2 on the test split,
in line with the original checkpoints re-evaluated by the same code (93.5 / 94.9).

The ATLAS-1 PointMIL(DGCNN) instance model re-trained with the current OpenPoints recipe
reaches 83.2 / 82.5 / 82.5 mACC / oACC / F1 on the test cells, the same as the original
checkpoint evaluated by this code (83.1 / 82.5 / 82.4). A run with an earlier version of the
config (selection on the validation subset, weight decay on all parameters) reached 82.0 /
80.8 / 80.7, which is why those two OpenPoints details are part of the recipe.

The RBC DGCNN and RBC Transformer additive rows re-train the folds whose original
checkpoint was not found (DGCNN: additive fold 4, attention folds 3 and 4, conjunctive
fold 4, instance folds 3 and 4; Transformer additive fold 0), so that every RBC model has
5 folds; the paper value next to them is the published 5-fold (or 4-fold) mean.

The PointMLPElite rows on IntrA and RBC are new 5-fold runs (the paper used one fold
each). They were trained with an earlier version of the configs: 100 epochs for every
head, and weight decay on all parameters. The current configs use the schedules of the
original runs and exempt biases and normalisation weights from weight decay, as
OpenPoints does. The paper value next to them is the single-fold value; for RBC the
paper does not say which pooling produced the PointMIL(PointMLPElite) row, so it is
shown next to the global-average-pooling run.

## Determinism

`seed_everything` seeds Python, NumPy and PyTorch, sets `cudnn.deterministic`, and
`DataLoader` workers are seeded. Remaining sources of non-determinism on GPU:
`torch.topk` tie-breaking in the k-NN graphs (identical coordinates), the
scatter-based gathers of the DGCNN edge features, and cuDNN kernels for 1x1
convolutions when deterministic algorithms are unavailable. Re-running a config with
the same seed on the same GPU reproduces the training curve closely but not bit for bit.

Measured: two runs of `configs/smoke/synthetic_transformer_conjunctive.yaml` with
`--seed 42 --device cpu` for 3 epochs produced identical per-epoch accuracies and
F1, training and validation losses that agree to 8 significant digits, and final weights
that differ by at most 8.3e-4 (absolute). On CPU the residual difference comes from the
summation order of multi-threaded BLAS reductions, not from the random number streams
(Python, NumPy, PyTorch and the `DataLoader` workers are all seeded).
